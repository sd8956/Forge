## Where the pipeline got stuck

1. **Permission prompts from how agents use Bash** (run 1: 12 prompts). Claude Code asks for permission,
   even in `acceptEdits` and with an allowlist, when a Bash command contains heredocs, `python3 -c`, shell
   variables, `$(...)`, or `cd` before `git` ("expansion obfuscation", "variable can't be checked"). Agents did
   all of these. My own `security-scan` skill told them to use variables.
2. **osv-scanner scanned nothing** in run 1. Task worktrees live under `.worktrees/`, which the main checkout
   ignores, so a recursive `osv-scanner -r .` skips the whole tree and exits 128 ("No package sources found").
   The security agent reported "no lockfile", but the lockfile was there. Fixed with `--lockfile`.
3. **Denying a prompt interrupts the turn.** After I denied `ls ~/.claude/skills`, the session sat at "What
   should Claude do instead?" until I typed an instruction.
4. **`needs_human` is sticky until the report.** When a person answers a prompt, nothing tells the backend the
   step is running again. The step stays `needs_human` until it reports, so a second prompt in the same step
   produces no state change. My operator monitor had to read panes to notice it.

## Bugs found by the tests before the real runs

- Same tmux name for every attempt of a step: the delayed close of attempt n killed attempt n+1
  (`resume` after exhausted security). Names are now `forge-<TASK>-<step>-<attempt>` (ADR 0004).
- **Found by CI (Node 22):** `node --test test/` runs nothing on Node 22, which reads the arguments as file
  patterns, so `make check` failed every development report. The fixture now passes `test/*.test.js`.
- **Found by CI (load):** `sweep` took the tmux session list before reading the live steps, so a step launched
  in between was marked `session_vanished` and retried. It now reads the steps first (deterministic unit test).
- Under parallel test load, a `kill -9` could land while a step was still `queued`. The backend handled it
  correctly (`orphaned_before_launch`); the test was fixed to wait for `running`.

| Engram | Only plan, design and security saved memories; development, e2e and pr saved none | Make the save step concrete per step (for example, development saves conventions it had to infer) |

## What I would change before Phase 2

1. **A `PreToolUse` HTTP hook** in the step settings: the backend answers `deny` for Bash commands that
   write files or use expansions, with the reason as feedback. That turns the worst source of prompts into
   an automatic, logged correction.
2. **Leave `needs_human` when the person answers.** Use `PostToolUse` (or `UserPromptSubmit`) hooks to move
   the step back to `running`, so the panel (and any monitor) sees a second prompt as a new event.
3. **Embedded terminal first.** Phase 2's panel must let the person answer prompts. In F1 that happened
   through `tmux attach` and `send-keys`, which is the most frequent human action.
4. **Stacked tasks.** TASK-002 depends on TASK-001, which is not merged, so its PR carries TASK-001's commits.
   The Phase 3 DAG ("start when dependencies are merged") avoids that. Until then, run dependent tasks only after
   the merge.
5. **Prompt budget per step.** Record operator prompts per step as a metric (they are already events), and
   show it on the card. It is the best signal of an agent or skill that needs work.
